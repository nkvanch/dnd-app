# Grimoire — Road to 1.0
*Companion to RELEASE_AUDIT.md and VISION_ASSESSMENT.md. Strategy + step-by-step execution plan.*
*Current build ≈ 0.9. Everything below is ordered — each phase gates the next.*

---

## THE ONE-LINE PLAN

**1.0 = legal-clean SRD content + own package ID + privacy policy + death
saves + backup/export + onboarding with demo character + one closed beta
round.** Everything else is post-1.0.

**Hard rule: no public promotion until Phase 1 (legal) is done.** Creators
covering the app puts eyes on it; WotC has a history of C&Ds against tools
shipping non-SRD content. Legal-clean first, loud second.

### Step 1.3 — Filter non-SRD from the public build  ✅ COMPLETE
- [x] **Design decision (deviates from the original plan, deliberately):**
      the original wording ("export ALL_SPELLS filtered to srd === true for
      anything built for distribution") would have hard-filtered EVERY
      build, including the one Nick actively uses at his own table with
      non-SRD content — that would have been a real functionality
      regression, not a legal fix. Implemented as a **build-target-aware
      filter** instead:
      - `src/content/spells/index.ts` now imports `ALL_VAULT_SPELLS` from
        `generated.ts` (previously NOT WIRED IN AT ALL — the entire Step 1.1
        audit had zero effect on the running app until this step).
      - New `FULL_SPELL_LIBRARY` export: every spell, unfiltered (44 inline
        originals + 146 hand-authored + 487 vault-sourced = 677 total
        entries feeding in, before dedup).
      - New `EXPO_PUBLIC_SRD_ONLY` env var, read via `process.env` at
        runtime. `eas.json`'s `production` build profile now sets it to
        `"true"`; `development` and `preview` profiles leave it unset.
      - `ALL_SPELLS` (the export everything else in the app already
        imports) = `FULL_SPELL_LIBRARY` unfiltered when `SRD_ONLY` is
        false/unset, or filtered to `srd === true` when true. Personal/dev/
        preview builds — including everything Nick runs today — are
        byte-for-byte unaffected. Only the eventual Play Store production
        build filters.

The phrase "X, Y, or Z, all/both detailed at the end of the class

full page and confirming the actual detailed section exists (checking the
page's own table of contents is a fast proxy — 5thsrd.org's TOC only lists
subsections that actually exist on the page).

## 🆕 FEATURE DESIGN: Wild Shape

*Added as a tracked goal. Executability: **NOW** — fits the existing
architecture unusually well. Estimated size: one meaty batch (medium-large),
comparable to the house-rules system build.*

### Why this is a good fit, not a bolt-on
The type system already has `AbilityEffect = { type: 'transform'; formId: string }`
scaffolded in `FeatureActivation`/`AbilityEffect` — this was anticipated.
More importantly, the *shape* of Wild Shape (temporarily override an
entity's stats without touching its base data, then cleanly revert) is
**exactly the pattern `DmOverride` already implements**: apply on top in
`recomputeDerived`, never mutate `entity.stats`/`entity.features`, cancel
restores automatically. Wild Shape can reuse that philosophy at a higher
level instead of inventing a new one.

### Scope for v1 (Circle of the Land/Moon core mechanic, book rules only)
- New content type `BeastForm`: id, name, a small stat block (STR/DEX/CON,
  AC, HP formula or flat, speed, senses, movement, a short list of
  `ActionCard`-compatible attacks as `AbilityEffect[]`), and a `maxCr`
  gate (SRD beasts only — Wolf, Brown Bear, Giant Spider-tier content is
  in the SRD monster list, so no legal issue here).
- New entity field: `wildShapeState: { active: boolean; formId: string | null;
  beastHp: number; expiresAt: DurationTracker } | null`.
- Feature: "Wild Shape" — `FeatureActivation` (bonus action, resource cost =
  a `wild_shape_uses` `CustomResource`), `abilityEffects: [{ type: 'transform', formId }]`.
- Pipeline change: when `wildShapeState.active`, `recomputeDerived` swaps
  AC/speed/senses/movement/attacks to the beast's, keeps the player's own
  INT/WIS/CHA-derived values (mental saves, class features, proficiency
  bonus) per the book rule — same "apply on top, never mutate base" pattern
  as `DmOverride`, just swapping a different layer.
- Revert triggers: manual (bonus action, or free per book at low level),
  automatic at 0 HP in beast form (reverts to human form at 0 HP, no
  carryover damage — this is the actual 5e rule), or `DurationTracker`
  expiry (half druid level in hours, minimum 1).
- Resource recharge: uses restore on long rest (short rest at higher Circle
  of the Moon levels — a `bonusFeatEveryLevel`-style house-rule-adjacent
  hook if you want it configurable later, but book default is fine for v1).

### Explicitly out of scope for v1 (cut list, keep it shippable)
- Custom/homebrew beast forms via the builder UI — v1 ships a small curated
  SRD beast list (5–8 forms covering low/mid level play), matching the
  existing "small builder, real mechanics" pattern from race/item builders.
- Swimming/flying/climbing form auto-selection logic, encumbrance
  interactions, or attack-roll automation — the app doesn't resolve attack
  rolls anywhere yet (see RELEASE_AUDIT.md crit-mode note), so beast attacks
  display as action cards with damage dice, same as every other attack in
  the app today. Consistent, not a regression.

### Where it fits the roadmap
Not a 1.0 gate — the app is legally/functionally complete without it. But
because it reuses the `DmOverride` pattern so directly, it's cheap relative
to its demo value (shapeshifting is exactly the kind of feature that reads
well in a YouTube demo). Candidate for 1.0 stretch goal; hard fallback to
early 1.1 if Phase 1–4 run long. Do not let it delay Phase 1.

## POST-1.0 BACKLOG (resist until shipped)
- **Wire generic magic item bonuses** — discovered while auditing what
  actually influences stats (2026-08-04): almost none of the 835-item
  imported magic item catalog (`importedItems.ts`) has real mechanical
  effects. `scripts/parse_items.py` only generates `abilityEffects` when an
  item has a `Damage:` field (i.e. weapons) — every other item, including
  ones that obviously should modify stats (Ring of Protection, Cloak of
  Protection, Bracers of Defense, Belt of Giant Strength, Headband of
  Intellect, +N armor/weapons/shields), becomes a purely descriptive feature
  with `effects: []`. Not "fake functionality" (nothing pretends to work),
  but a real, currently-undisclosed gap — equipping a Ring of Protection
  right now does not change AC or saves.

  **Why this needs a separate mechanism, not a parser fix:**
  `importedItems.ts` is auto-generated from free-text descriptions ("Items
  with descriptions.md") — regex-parsing reliable numeric bonuses out of
  hundreds of varied description strings is fragile and error-prone at that
  scale. The maintainable approach is a **hand-authored override layer**,
  same spirit as `CORE_ITEMS` already taking precedence over
  `IMPORTED_ITEMS` on id collision:
  - A curated `id → extra effects` map (e.g. `ITEM_EFFECT_OVERRIDES` in
    `src/content/items/index.ts`) applied on top of the auto-imported base
    item at load time, not by editing the generated file.
  - **Tractable, high-value first batch** (regular patterns, cover a lot of
    ground): the `+1/+2/+3` weapon/armor/shield family (very regular
    naming, straightforward `stat_modifier` bonus to AC or the existing
    weapon damage/attack effect), Ring/Cloak of Protection (+1 AC and all
    saves), Bracers of Defense (+2 AC, conditional on no armor/shield worn
    — needs a conditional-effect check, more involved), the ability-score-
    setting family (Belt of Giant Strength, Gauntlets of Ogre Power,
    Headband of Intellect, Amulet of Health — these SET a score to a fixed
    value rather than add to it, which may need a new effect operation if
    `stat_modifier` only supports `add`/`multiply` today — check
    `engine/types.ts` before starting).
  - **Explicitly out of scope / stays description-only by nature**: anything
    granting advantage on checks (Cloak/Boots of Elvenkind) unless the
    engine already has an advantage-grant effect type (check first), and
    narrative/utility items (Deck of Many Things, Bag of Holding, Portable
    Hole) that don't map to a stat at all — these are correctly
